## Public API and example

- `SdTableRowMobileDefDirective<T>` and `SdTableRowMobileDefContext<T>` are exported from the table and components entry points.
- Optional `SdTableOption<T>.mobile.rowLabel(row)` supplies visible and accessible row labels. Fallback is a primitive `rowKey`, then a meaningful row ordinal.
- `SdQuickAction.contained` supports the action presenter inside the table's own scroll container.
- [Complete standalone OrdersComponent](orders.component.ts) is extracted verbatim from the [source component documentation](../../../versions/v19/projects/sdcorejs-angular/components/table/sd-table.md). It includes imports, typed data/options, the mobile template, row commands and an async bulk callback.

The bare `sdTableRowMobileDef` attribute works, but its `item` defaults to `any`. Use `[sdTableRowMobileDef]="tableOption"` for checked generic inference. The compiler check includes a deliberate nonexistent `Order` property and requires that compilation to fail.

## Decisions and behavior

The Core viewport service chooses one row renderer. Data, filters, sort, paginator, selection, identity and expansion remain in the same table instance. Resize does not fetch or reapply defaults. Eligibility is prepared by shared utilities before either renderer runs; it does not depend on desktop pipe side effects.

Active row commands and selected rows are independent. Each table owns one contained action presenter and its More sheet. Actions receive the existing row or full-selection payload, respectively. Promise callbacks block duplicates and preserve selection on either outcome; the consumer decides which successful rows to remove and when to reload. The documentation includes partial-success handling.

Group headers, loaded/visible tree selection scope, custom slots, command headers, footer totals, filter, sort, paginator, export and drag handles retain their existing data contracts. A shared MatSort and paginator remain available even when the table starts directly on mobile.

## Reproduce the browser checks

Run from the repository root after building v19 and showcase, using Node 22.22.3:

```powershell
python .sdcorejs/memories/table-mobile-evidence/serve-showcase.py
# In a second terminal:
node .sdcorejs/memories/table-mobile-evidence/verify-browser.mjs
node .sdcorejs/memories/table-mobile-evidence/verify-integration.mjs
```

The browser scripts use an existing Playwright installation and the installed Chrome channel. Set `SD_PLAYWRIGHT_MODULE` to its module name or absolute file URL when it is outside the default module resolution path. The server binds only to `127.0.0.1:4300`, serves the built showcase and maps `/docs/` to the existing archive read-only. It does not generate or publish archives.

The showcase ships a light Material theme. Dark screenshots use the additional consumer Material theme fixture in [dark-theme.scss](dark-theme.scss) / [dark-theme.css](dark-theme.css), with Core tokens inherited from it. This fixture is review evidence, not a new global showcase theme.

The local archive version index predates the 2.5 source showcase and can show “Retry versions” in the navigation. Live examples were verified at `/v/22.2.5/components/table/examples`; immutable `published-docs` and `published-pages` were not edited.

The strict consumer fixture declares CSS assets when checking the aggregate components barrel, which also exports CKEditor. This uses the [TypeScript ambient asset declaration pattern](https://www.typescriptlang.org/tsconfig/noUncheckedSideEffectImports.html); `strict`, `strictTemplates` and `skipLibCheck: false` remain enabled.

No dependency versions, lockfiles or release archives are changed. Screenshot provenance and integrity are recorded in [the capture manifest](screenshots.json).
